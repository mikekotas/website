Atlassian Forge · Jira Cloud

Release Readiness Gate

The problem

A team's pre-release checklist lived in a Confluence page. It was followed when people remembered, and the only evidence a check had happened was that somebody said so in standup. Jira's built-in workflow validators couldn't express the rules — things like "at least two different people approved, and the assignee isn't one of them".

What I built

A Forge app with a configurable rules engine. A scorecard on every issue shows which checks pass and why; blocking rules prevent a transition until they're resolved; each gated transition posts a structured audit comment. Project admins configure the rules themselves in a settings screen — nine rule types covering field content, regex formats, labels, issue links, blockers, due dates and multi-person approvals.

The decision that shaped it

Every rule evaluation lives in a pure module that imports nothing from the Forge platform. It takes plain objects and returns plain objects, so the whole rules engine is unit tested in under a second with no Jira instance and no mocks. The adapters around it stay thin enough to review by eye — and the same function that decides which buttons to render also decides whether the server honours the call, so the UI and the enforcement can't drift apart.

Google Apps Script · Cloud Firestore

Access Request Desk

The problem

Requests for access to production systems were raised in a shared spreadsheet. Anyone could edit any row, there was no record of who approved what, and "temporary" access was never actually removed. The obvious fixes all meant buying another per-seat tool for a process that runs a few times a week.

What I built

An internal web app on Google Workspace: staff raise a request, approvers review it, fulfillers mark it provisioned, and temporary access expires on its own. Every state change lands in an append-only audit trail. Requests past their SLA escalate automatically — with a tighter clock for sensitive systems than for an analytics workspace.

The decision that shaped it

There is no service-account key anywhere in the project. The script is attached to the same Cloud project as Firestore and authenticates through IAM, so there is no credential to leak and none to rotate — access is revoked by removing a binding. Identity always comes from the session, never from the request payload. And the whole authorisation model lives in one platform-free module, which is the only way to get it under test at all in an environment with no test runner.

Google Cloud · Jira · Node.js

SaaS Renewal Tracker

The problem

Companies don't lose money on SaaS because the renewal date surprises them. They lose it because the cancellation deadline passed weeks earlier and nobody noticed. A contract renewing on 1 June with 30 days' notice has to be cancelled by 1 May — and on 2 May the decision has already been made for you. That date isn't on the invoice and isn't in anyone's calendar. The spreadsheet that tracks renewals stores the notice period; it never uses it.

What I built

An internal web app on Google Cloud, wired into Jira in both directions. A dashboard shows annual spend and spend at risk — money on auto-renewing contracts whose deadline has passed or is within a week. A daily job computes every real deadline and raises a Jira task for the contract's owner at 90, 60, 30 and 7 days out. The owner answers by adding one label and closing the task; a webhook updates the tracker, rolls the term forward or cancels it, and records who decided and when.

The decision that shaped it

Two places where idempotency costs real money, both with dedicated tests: running the daily job twice must not raise a second Jira task, and applying a decision twice must not roll the contract forward two years — which would silently push the renewal date out of range and stop it being watched at all. Jira delivers webhooks more than once, so the second one isn't hypothetical. And three callers reach the service, each proving identity differently: Google Sign-In for people, verified OIDC for the scheduler, and a constant-time shared secret for Jira, which can't mint a Google token.

How I work

Internal tools fail slowly. These are the habits that stop it.

Decisions in the middle, I/O at the edges

Business rules go in modules that import nothing from the platform, so they can be tested in milliseconds instead of by clicking through a UI. It's also what makes the code reviewable by someone who doesn't know the platform.

The client is never the control

Browser-side validation is for speed of feedback. Every rule is enforced again on the server, identity is always derived from the session, and permission checks fail closed.

No credentials in code

Platform identity and secret managers over key files and environment variables. There should be nothing to leak, and rotation shouldn't need a redeploy.

Quiet by default

A tool that notifies on everything gets muted within a week. I fingerprint outcomes and only speak up when something actually changed — which also keeps the platform bill down.

Designed for the bad day

Overlapping runs, rate limits, half-written batches, records that don't match the documentation. These aren't edge cases in an integration — they're Tuesday. Each one gets a named, tested behaviour.

Handover, not dependency

A README that explains the decisions, not just the commands. Tests that document intent. Configuration your team can change without me.
